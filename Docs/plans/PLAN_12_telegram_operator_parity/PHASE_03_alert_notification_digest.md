# Phase 03: Alert Notification and Digest Routing

**Priority**: P1  
**Status**: Completed  
**Implemented On**: 2026-04-13  
**Depends On**: PLAN_11 Phase 05 runtime event substrate

---

## 1. Goal

Route high-signal runtime events to Telegram so mobile operators learn about
problems without polling manually.

---

## 2. Implemented

### 2.1 Shared runtime-event persistence

Modified files:

- `src/ds_agent/runtime/runtime_event_log.py`
- `src/ds_agent/api/ws_handler.py`

Implemented:

- `RuntimeEventLog` now supports workspace-scoped file-backed persistence
- runtime events are shared across processes through the workspace runtime root
- `AppState` now opens the persisted runtime event log for the current workspace
- workspace changes rebind the runtime event log alongside transcript/checkpoint/policy stores

This is what makes Telegram able to consume alerts generated by the API daemon
without requiring a direct in-memory listener.

### 2.2 Telegram alert polling and push routing

Modified files:

- `src/ds_agent/gateway/telegram_runner.py`

Implemented:

- background Telegram poller for shared runtime events
- operator-chat registration based on chats that have interacted with the bot
- live push notifications for high-signal events:
  - `recovery.awaiting_approval`
  - `recovery.resume_recommended`
  - `pipeline.health.degraded`
  - `model.monitor.degraded`
  - `system.resource.pressure`
  - `system.resource.normal`
  - `policy.dispatch_failed`
  - important `policy.suppressed` cases
- per-kind throttling to avoid pressure/policy spam

### 2.3 Alert digest command

Modified files:

- `src/ds_agent/gateway/telegram_runner.py`

Implemented:

- `/alerts [count]` digest command
- digest lines show:
  - severity
  - event kind
  - target session
  - relative age
- help text updated to include the new alert surface

### 2.4 Regression coverage

Modified files:

- `tests/unit/infrastructure/test_telegram_runner.py`
- `tests/unit/infrastructure/test_runtime_persistence.py`

Implemented:

- `/alerts` digest coverage
- live runtime alert push coverage
- pressure alert dedupe coverage
- cross-instance runtime-event persistence coverage
- runtime-event ordering coverage

---

## 3. UX Rules

- Telegram should receive only actionable alerts by default
- repeated pressure/status flapping must be deduplicated or throttled
- messages must name the affected session/run when available
- alert digests should summarize first, then offer drill-down commands

## 5. Exit Criteria

- Telegram receives high-signal runtime alerts
- operators no longer need to poll Electron for basic incident awareness
- notification volume remains controlled enough for daily use

## 6. Notes

- Telegram still uses command-first UX.
- Inline or threaded alert actions were intentionally deferred.
- Live push is routed to chats that have already interacted with the bot.
